# Review: issue #58, a size limit for the session file on resume

Scope: the working-tree diff for issue #58 (`lib/helyx/session_file.ex`, its test, the bounds rows in `docs/features/coding-agent.md`).

Bounds sensor, every round: `bounds sensor skipped: TYPESAFE_API_KEY is not set`.

The branch had no commit between rounds, so every rerun round got the whole working-tree diff plus the invariant of the fix, not a diff from the commit before the fix.

## Round 1 (first round, full: simplify + three axes)

- **Simplify**: applied one fix, `read_up_to/2` flattened into one `with`. Skipped: reuse of `Helyx.Tool.read_file/1` (fixed 10 MB limit, UTF-8 rule, string errors, and it rejects where the header scan needs a prefix; a shared helper waits for a third caller); a `stat` size check before the read (the bounded read is the structural check; an over-limit file costs one 64 MiB read, once); a line read for the header (the bound is the ticket); fewer boundary tests (the checklist asks for at, under, over, multibyte).
- **Standards, confirmed**: the header-scan row said the number of files is unbounded and named no ticket. Fixed: ticket #62 filed and cited. Applied from the judgement calls: the `@doc` says `:max_bytes` is a test seam; the test helper is `overwrite_session/2`. Skipped: `{:too_large, max_bytes}` without text (the `{:invalid_file, text}` precedent, and the triage asks for the text).
- **Spec, confirmed**: the "one byte over" test was six bytes over. Fixed: it appends one byte. Skipped: "64 MiB" in the text in place of the byte count (the option changes the limit, so the text prints the limit in use). Noted, out of scope: `mix helyx` prints the error with `inspect/1`.
- **Failure-path, confirmed**:
  1. A valid header plus 60 MiB of `"\n"`, under the limit, made `resume` use 2172 MiB: `String.split(raw, "\n")` built a list of all lines before the first bad line stopped the parse. Fixed: `parse/3` walks one line at a time and stops at the first line that does not parse; `repair/3` matches on a tail tag. Test: the same shape under a 16 MiB `:max_heap_size`.
  2. A bad `:max_bytes` (`0`, `-1`, `1.5`, `nil`) came back as `{:too_large, _}` or `{:invalid_file, _}`. Fixed: `resume/3` hands the option to a guarded `resume_within/3`, outside the rescue, so it raises.

## Round 2 (rerun, full round: the fix adds functions and changes more than 15 lines)

Invariant named in the briefs: the memory that resume uses is a bounded multiple of the byte limit, a bad option is never reported as a bad file, and a rejected file is never mutated.

- **Simplify**: clean on reuse, simplification, and efficiency. Altitude: the decoded entries still cost a multiple of the file; the first answer was a stated multiple in the bounds row, which the review below proved wrong.
- **Standards**: no hard findings. Judgement calls declined: the names `resume_within` and `read_up_to`, the `:eof` sentinel and the repeated `Enum.reverse` in `parse/3`.
- **Spec and failure-path, confirmed, same finding**: one long line still amplifies inside `JSON.decode/1`: 60 MiB of `[` used 2523 MiB, an array of `0,` 1294 MiB, 60 MiB of short entries 727 MiB. This is the second finding on the memory mechanism, so the two-findings rule applies: no further path patch. The mechanism fix (a parse process under a heap cap, or line and entry limits) needs values the ticket does not state. Filed as #64; the bounds row states it as open with the measured range. The line walk stays: it removes the 36 times cost of the list of lines and holds for its reproduction (peak under 1 MiB).
- **Spec**: the rewritten `parse/3` and `repair/3` keep the old repair behaviour in every case traced (clean, no newline, torn after multibyte, bad line mid-file, `"bad\n"` last, `"h\n\n"`, empty file).
- **Failure-path, confirmed**:
  1. `max_bytes: 2 ** 70` returned `{:error, :einval}`. Fixed: the guard is `max_bytes in 1..@max_bytes//1`, so the option only lowers the limit.
  2. A last entry without its newline in a file exactly at the limit resumed once, got its newline, and was `{:too_large, _}` ever after. Fixed: `repaired_size/2` counts that newline before anything is written. Test added.

## Round 3 (rerun, full round: in doubt under the two-findings rule; the fix itself is one code file, about 12 lines)

Invariants named in the briefs: a repair never makes a file that the next resume rejects, and a rejected file is never mutated; a bad `:max_bytes` is never reported as a bad file.

- **Simplify**: clean. Declined: one size check before the parse that adds a byte when the file lacks a final newline (it rejects a torn file at the limit that the repair would shrink); `1..@max_bytes` without `//1` (cosmetic, and precommit was in progress on the code).
- **Standards**: no violations. Judgement calls accepted: two adjacent dispatches on the tail tag, the `kept_bytes, tail` pair.
- **Spec**: all acceptance criteria met; both invariants hold. Doc findings, fixed: the #64 row now says the decode heap of the whole file is open, 12 to 42 bytes per file byte; the header row no longer claims a maximum header length; the window between `File.stat` and `File.open` is stated as open, ticket #65 (not reproduced in 200,000 swaps in round 1).
- **Failure-path**: both reproductions pass. Two findings, both present before this diff and not applied:
  1. Four concurrent resumes of a file whose last entry lacks its newline each append one, and the next resume rejects `header\n\n\n\n`. This is the no-lock hole the feature doc already states as open and accepted for checkpoint one ("Nothing locks a session file").
  2. A `dir` or `cwd` that is not a string comes back as `{:invalid_file, _}` through the whole-function rescue. The spec types both as strings, the one caller passes strings, and the rescue is the module's design from the session-file review.
