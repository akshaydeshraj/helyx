# Review: issue #37, one owner for the lifetime of a command

Scope: the working-tree diff for issue #37 (links and the port watchdog: `lib/helyx/hands.ex`, `lib/helyx/session.ex`, `lib/helyx/tool.ex`, `plugins/tool_bash`, tests, ADR 0004, the feature doc, the checklist).

## Round 1 (first round, full: simplify + three axes)

- **Simplify**: applied a batch `kill(1)` invocation (one fork per group set). Skipped a batch `kill -0` fast path: multi-target kill exit semantics vary by platform.
- **Standards**: no hard findings. A stale-citation claim (the bash `ponytail:` marker) was a false positive; the marker exists at `bash.ex`.
- **Spec**: no conflicts with the ticket or ADR 0004.
- **Failure-path, confirmed**: a command that contains a NUL byte is cut silently at the port boundary (port arguments are NUL-terminated C strings) and reports success for something that did not run as given. Fixed: `run/2` rejects a command with a NUL before the port opens; test added.
- False positive, not applied: a claim that the hands' catch-all `EXIT` clause breaks the link chain. OTP parent-exit handling covers it; the session-kill test proves it.

## Round 2 (rerun on the NUL fix, full round: the fix touches two code files and adds `run_command/2`)

Invariant named in every brief: a string handed to the OS boundary is used exactly as given, or the call returns an error; nothing at the boundary silently alters or truncates it.

- **Simplify**: clean. Sibling tools' file APIs reject NUL paths with `:badarg`, so no shared guard is warranted; bash is the only truncating boundary.
- **Standards**: no hard findings. `cond` over pattern matching is accepted: `String.contains?/2` is not guard-safe.
- **Spec**: no conflicts. Asked for a bounds-table row for the NUL constraint; added.
- **Failure-path**: the original reproduction passes; boundary shapes (first byte, last byte, NUL-only, empty, multibyte, invalid UTF-8) hold. **Confirmed**: a NUL in `cwd` is cut silently by the port's `{:cd, cwd}` option — a second finding on the same mechanism. Per the two-findings rule, the fix went to the mechanism: one `cond` in `run/2` checks every string that reaches the port. Minor, skipped: read/write/edit error messages interpolate the raw path, so an error string can carry a NUL; it is valid UTF-8, harmless in the transcript, and the verbatim path aids the model.

## Round 3 (rerun on the mechanism fix, full round: the two-findings rule applies to it; the fix itself is one code file, ~10 lines)

- **Simplify**: clean. The `cond` is the right altitude; the hands' `File.dir?` covers the real flow, the tool guard covers the boundary.
- **Standards**: no hard findings. The two near-twin branches keep distinct error messages on purpose.
- **Spec**: no conflicts; the bounds row matches the table's style and the code; no scope creep.
- **Failure-path**: the reproduction passes; launcher argv carries no NUL; the real session flow cannot reach `Bash.run` with a NUL cwd (`File.dir?` is false).
  - **Confirmed, pre-existing, ticket #52**: a cwd the port cannot enter (removed between the hands' check and `Port.open`) yields an ok result with exit code 2 for a command that never ran, indistinguishable from a genuine bash exit 2. Not introduced by this diff; recorded as an open hole in the feature doc's bounds table, per the checklist's race rule.
  - **Skipped**: a charlist cwd now raises `FunctionClauseError` in the guard path. The `Helyx.Tool` callback types cwd as `String.t()`; no caller passes a charlist, and the hands catch the raise into an error result.

Round 3 produced no code change (a ticket and Markdown only), so the loop ends here.

Precommit note: Dialyzer flagged an opaqueness break in `clear_stuck/1` (a struct rebuilt with a literal `MapSet.new()` passed into `kill_and_wait/3`). The re-KILL was inlined there instead; the behaviour is identical and the existing stuck-group tests cover it.

## Standing skip rationales (design calls, recorded once)

- Blocking `select` + SIGCHLD in the watchdog rejected as racy (a signal before select blocks is lost); the 50 ms poll tick is deliberate.
- `read_marker` tolerates a stream that does not start with the marker, so a perl failure surfaces as output instead of hanging.
- The `check/1` seam on the bash tool stays for the acceptance test of a perl-less system.
- Per-owner Task.Supervisors are out of scope; Core's one supervisor with links does the ownership work.
- A zombie-aware `alive?` predicate was rejected for portability; the watchdog's blocking reap makes it unnecessary.
- Chat and quit while a group is stuck are structurally unaffected (the stuck set gates only tool calls); no extra test.
