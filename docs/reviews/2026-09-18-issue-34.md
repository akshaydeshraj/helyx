# Review: ticket #34, tool results are valid text before they enter the transcript

Simplify, then three axes on the working tree before commit, per `/ship`. One reduced rerun round followed the fixes.

## Simplify

- The scrub sat at three call sites in `run_tool/3`, and the `:DOWN` crash path bypassed it. Fixed: one `scrub/1` in `deliver/3`, the single point where every result leaves the hands, for the ok, error, catch, and crash paths alike.
- Unconditional `String.replace_invalid/1` copied every valid result. Fixed: a `String.valid?/1` fast path. Measured: `replace_invalid/1` copies even valid input and is slower than the scan, so the guard is not speculative.
- Skipped: deleting the OpenAI composition test. The ticket requires it, and feeding pre-scrubbed text instead of the hands' own output would make it tautological.
- Skipped: replacing the feature doc bounds row with a sentence. The ticket names the bounds table as the home of the replacement policy.

## Standards

- The one-row bounds table with a pointer at module docs broke the checklist rule that the feature doc states every bound. Fixed: the table is backfilled with the file read, truncate, bash buffer, and kill wait bounds.
- No multibyte-pass test for the new UTF-8 gate. Fixed: `read_file/1` multibyte test in the root suite; the truncate-meets-invalid-bytes case landed in the rerun round.
- The moduledoc reflow in `Helyx.ModelContext.Default` left an orphan line. Fixed.
- Deferred: renaming `scrub/1` (standard vocabulary for the operation) and `bounded/1` (private, rename if touched again). The `BinaryTool` test module name keeps its suffix; a bare `Binary` in a provider test reads worse.
- The claim that `String.replace_invalid/1` is a no-op on valid text was checked and is wrong; the fast-path guard stays.

## Spec

- The edit tool rejects invalid UTF-8 through the shared reader but had no test. Fixed: a test in `plugins/tool_edit`.
- "The session accepts the next prompt" was untested at the session seam. Fixed: the binary-tool session test issues a second prompt.
- The scrub can grow a truncated result past the truncate cap, and the bounds row stated no ceiling. Fixed: the row states the true universal bound, three times the byte size, after the rerun round measured the "three times the cap" wording short by the truncation notice.
- The `model_context_default` filter removal is outside the two named seams. Kept: the filter is dead once the shared reader rejects invalid UTF-8, and its own test still passes.

## Failure path

No confirmed defects, both rounds. Probed with throwaway tests under `.scratch/review/`, all deleted: the catch and `:DOWN` paths with invalid bytes; `read_file/1` at the 10 MiB limit with and without invalid bytes, and a 4-byte character whole and cut at the limit; a partial multibyte tail from a tool; invalid bytes in an `{:error, text}` result; truncate cutting mid-multibyte on valid text, head and tail; a bypass hunt (only the hands send `{:tool_result, ...}`; the session's synthesized `aborted` result is static ASCII).

Measured, led to a doc fix: a 60,000-byte all-invalid bash result scrubs to 153,627 bytes, over three times the 51,200-byte cap because of the truncation notice; the bounds row now states the growth relative to byte size, which holds.

Accepted, stated in the bounds table: the bash rolling buffer cuts on a byte offset, so the cut can land inside a character and the fragment becomes one U+FFFD at delivery. Repairing intermediate buffers would misfire on chunk boundaries that legitimately split characters mid-stream, and the result already says its output was cut.
